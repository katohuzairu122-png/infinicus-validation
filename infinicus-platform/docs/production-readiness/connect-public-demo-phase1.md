# Connect the public demo to the real backend — Phase 1 (backend)

Scope: move the public site's "Public Idea Mode" simulation off pure client-side JS and onto the real, Postgres-backed platform, through Data Acquisition (normalization) → Simulation → AI Decision Intelligence, with signup required first. See `docs/launch/` for the overall phased plan (Phase 1 backend / Phase 2 frontend / Phase 3 OCI deployment / Phase 4 live wiring).

## What this phase built

- **`packages/simulation-engine`** — the exact Monte Carlo algorithm from `index.html`'s `simulate()`/`monteCarlo()`/`simulateLong()`/`monteCarloLong()`/`calcScores()`/`computeVerdict()`, ported verbatim (same formulas, same industry-profile tables, same capital-adequacy verdict gate) into TypeScript, with 20 new unit tests. Reused, not reinvented — behavior parity with what's live today.
- **`packages/workflow`'s `SimulationOrchestrationService`** — orchestrates a real run through the existing (previously entirely unwired) Simulation domain: `SimulationModel`/`Version` → `Scenario`/`Version`/inputs → `Request` → `Run` → percentiles/iteration-summary → `Result`/`Version`/metrics → publish, then an ADI `DecisionQuestion` → `DecisionCase` → `DecisionRecommendation` carrying the verdict. Business Operations, Business Intelligence, Digital Twin, Approved Business Action, and Continuous Learning are deliberately not touched — they all presuppose an existing, operating business with history, which a first-time idea evaluation doesn't have.
- **New routes**: `POST /v1/businesses` (was missing entirely — no route created a business before this), `POST /v1/businesses/:businessId/simulations` (async: creates the run, returns immediately), `GET /v1/businesses/:businessId/simulations/:runId` (poll for status/result).
- **CORS**: `@fastify/cors` registered (none existed before), explicit allowlist (`corsAllowedOrigins` config, defaults to the live site's real domain from the root `CNAME` file), never `"*"` — this API accepts a bearer token and tenant-scoping headers.

## Genuine pre-existing gaps found and fixed along the way

1. **No HTTP route created a business at all.** `BusinessRepository.create()` existed but nothing in `apps/api` called it. Fixed: `POST /v1/businesses`.
2. **Onboarding was only 1 of its own 6 steps reachable over HTTP.** `OnboardingService` has `beginOnboarding` (step 1) → `setBusiness` (step 2) → `assignOwner` (step 3, grants the 'owner' role) → `applySettings` (4) → `inviteMembers` (5) → `complete` (6), but only step 1 had a route. Without step 3, a caller can never get an active membership, and every other route requires one — the API had no way to actually finish signing someone up. Fixed: wired steps 2 (`POST /v1/onboarding/:onboardingId/business`) and 3 (`POST /v1/onboarding/:onboardingId/owner`), the two required for a caller to do anything else. Steps 4/5/6 remain unwired (settings/invitations/completion aren't required for any route's authorization checks) — a known, narrower residual gap.
3. **Real privilege-escalation risk found while wiring step 3.** Neither `setBusiness` nor `assignOwner` verified the caller was actually the user who started that onboarding attempt — an authenticated caller who supplied a real (but not their own) `tenantId`/`onboardingId` pair would have been able to grant *themselves* the 'owner' role in *someone else's* tenant. Not exploitable before this build (both methods existed only in the service layer, never reachable over HTTP), but genuinely exploitable the moment they were wired to routes. Fixed: `OnboardingService` now verifies `progress.initiatedBy === ctx.userId` in both methods before proceeding (new `OnboardingNotInitiatorError`, 403).
4. **No self-service account activation exists.** `POST /v1/auth/register` leaves a user in `pending` status; only `UserRepository.activate()` (called directly in tests, never over HTTP) moves it to `active`, and login rejects a pending account (`AccountNotActiveError`, 403). There is no email-verification flow, no activation route, and no email-sending capability anywhere in this backend (the *old* static site's Cloudflare Functions have their own separate Resend integration for nurture emails — entirely unrelated to this Fastify API). **This blocks genuine self-service signup** — Phase 2's "require signup" flow cannot actually complete for a real visitor as the backend stands today. Not fixed in this phase (building real email verification is a separate, nontrivial feature); flagged here as the single biggest open blocker before Phase 2's frontend wiring can work against a real deployment rather than a test harness that activates accounts directly.

## Verification

- `pnpm turbo run build lint typecheck test` (whole workspace): all green.
- Live end-to-end HTTP test against a local Postgres instance: register → activate (direct DB, see gap 4 above) → login → begin onboarding → set business → assign owner → create business → start simulation → poll to `completed` → verdict `GO`, all result-shape invariants held.
- Spot-checked the actual database rows for that run (not just the HTTP response): `simulation_runs.status = completed`, a `published` `simulation_results` row with the right summary, and a `published` `decision_recommendations` row linked through a `recommended`-status `decision_case` — the full pipeline genuinely persists, not just computes in memory.

## Known simplifications (deliberate, not bugs)

- A fresh `SimulationModel`/`Version` is created per run rather than reused per business — `SimulationModelRepository` has no lookup-by-code method to find an existing one, and adding one plus the reuse logic was out of scope for this phase. Low cost today (a handful of extra rows per run); worth revisiting if per-run write volume ever matters.
- Only aggregate iteration summary + percentiles are persisted for the 500-run Monte Carlo, not all 500 individual iterations — `SimulationRunRepository.recordIteration()` exists for that but was deliberately not used, per BUILD-27's own already-documented per-iteration write-volume concern.
